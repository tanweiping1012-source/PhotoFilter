# 旅行照片筛选器任务卡（历史存档）

> 本文记录 PC-07 起每个任务**当时**的目标、范围与验收口径，用于追溯“为什么这么设计”。
> 它不是当前行为的权威定义——当前行为以[产品说明](../product/OVERVIEW.md)和[数据契约](DATA_CONTRACTS.md)为准。
> 文中的具体数值可能已被后续任务取代。

状态：`待办`、`进行中`、`已完成`。每张任务卡必须独立通过 `scripts/check.sh`，涉及真实照片时还必须通过源目录只读校验。

## PC-07 本地候选代表化

**状态：已完成**

- 用户故事：相似图或连拍图只把本地技术最优的一张交给最终 AI 比较，避免最终结果出现重复画面。
- 输入：完成本地分析的 `PhotoItem`、人工决定、最终目标 N。
- 输出：每个相似/连拍候选家族最多一个成员进入待评分池；已有人工作为 `keep` 的家族不再输出其他成员。
- 验收：重叠的连拍/相似组也只输出一个代表；最终结果若仍包含同家族照片则整轮结果不生效。
- 非目标：本地技术排序不替用户自动淘汰原图。

## PC-08 无分组照片覆盖

**状态：已完成**

- 用户故事：没有进入连拍或相似组的普通照片仍有机会进入 AI 评分。
- 规则：所有未分组、未人工淘汰的照片都具备参选资格；候选容量有限时按拍摄时间分段抽样，且候选池同时存在组代表和普通照片时至少保留普通照片席位。
- 验收：测试集中同时存在组照片与普通照片时，两类都进入候选池；候选说明展示普通照片入选数。
- 非目标：不把所有普通照片都上传给 AI；候选池仍受每个最终名额最多 5 张、全局上限限制。

## PC-09 项目化侧栏

**状态：已完成**

- 用户故事：每个日期文件夹是一项独立筛选项目，像 Codex 项目列表一样可以新建、切换和查看进度。
- 输出：左栏只承担项目导航和真实操作；移除不可点击的“待AI评分/AI评分结果”说明卡，改为可点击筛选入口。
- 验收：同一 App 会话可创建多个项目并切换；项目名称优先显示“上级目录 / 当前目录”；切换不会改写源照片。
- 约束：首个切片为会话内项目；跨 App 重启的安全书签持久化单独立项。

## PC-10 删除项目与缓存释放

**状态：已完成**

- 用户故事：用户能删除不再需要的筛选项目，避免照片状态和缩略图长期占用内存。
- 输出：删除前明确确认；删除后释放该项目状态、撤销历史和缩略图内存缓存。
- 验收：确认文案明确“不会删除原照片”；删除后项目从列表消失、活动照片数组释放、原目录哈希不变。

## PC-11 大图库交互与性能

**状态：已完成**

- 用户故事：浏览数百至数千张照片时，选择、滚动和切换筛选不被同步解码阻塞。
- 输出：缩略图离开主线程解码；缓存设置数量与内存上限；撤销只记录决定差异，不复制整份照片数组；窗口底部提供始终可见的保留/淘汰/恢复/撤销/导出操作。
- 验收：缩略图加载不会在 SwiftUI `body` 中同步解码；删除项目可清空缓存；常用动作不依赖隐藏快捷键。

## PC-12 项目持久化

**状态：已完成**

- 使用 macOS security-scoped bookmark 恢复用户明确创建的项目。
- 仅持久化最小项目元数据和人工决定，不持久化原图、API Key 或 AI 上传预览。
- 路径失效或权限撤销时清晰提示，不自动重新授权。
- 验收：设置目标和人工决定后完全退出 App，重开后恢复项目并重新分析，人工决定按相对路径合并；删除项目后持久记录与访问权限均释放；源目录哈希不变。
- 回归：`scripts/check.sh` 已覆盖跨启动恢复、目标与相对路径决定合并、删除项目、权限释放及最小磁盘状态，59 项测试全部通过。

## PC-13 AI 批次失败恢复

**状态：已完成**

- 用户故事：方舟偶发返回不合规结构时，长批次任务不会表现为无响应，用户可以看懂失败位置并只重试当前批次。
- 输出：响应外层、缺少工具载荷、载荷字段错误使用不同但不含原始内容的安全错误；格式与模型字段异常自动重试 1 次；仍失败时保留批次上下文并显示“重试第 N 批/放弃本轮”。
- 费用约束：自动重试仍是一次真实请求，发送确认必须披露最多增加 1 次请求与费用；每次尝试继续遵守 60 秒间隔。
- 验收：失败态不再显示无效的暂停按钮；重试从 `completedBatchCount + 1` 继续，不重复发送已完成批次；HTTP 权限、限流或模型配置错误不自动重试。
- 隐私约束：诊断只暴露失败阶段，不保存或展示方舟原始响应、图片、文件名、路径、理由或 API Key。

## PC-14 弹性候选池与同场景去重

**状态：已完成**

- 用户故事：待评分池不再为了达到 48 张而包含大量同场景照片，用户只为有独立价值的照片支付评分成本。
- 输出：取消会漏识别的哈希分带预筛；严格近重复之外增加两分钟内的本地同场景匹配；每个候选家族只输出一个代表；候选池按剩余目标的 2–3 倍弹性收敛。
- 验收：目标 12 张、强候选充足时最多选择 36 张；弱或未知候选只保留 24 张最低比较池；真实 299 张目录中截图标记的同场景照片不再同时进入待评分池。
- 隐私与性能：只复用内存中的低清灰度指纹，不上传、不落盘；真实目录验收必须通过源文件哈希前后对比。

## PC-24 MiniMax-M3 429 诊断

**状态：进行中**

- 问题：Token Plan Key 在首批 M3 请求中返回 HTTP 429，但 App 未识别 MiniMax 当前 `error.http_code/message/type` 响应形状，只显示模型权限通用提示。
- 证据：同一 Key 对 OpenAI 与 Anthropic M3 端点的无图片 1-token 请求均返回 429；响应安全分类为 `rate_limit`，排除图片尺寸、工具 schema、模型 ID 和端点错误。
- 修复：区分 Token Plan 与普通 API Key 的 429，提示检查 5 小时/周额度、动态限流或余额，并保留失败批次供人工重试。
- 费用边界：HTTP 429 不自动重试；诊断不展示 Key、照片、prompt、供应商 message、request ID 或原始响应。
- 验收：用 MiniMax 实际错误形状做无网络 stub 测试，对比预修复/修复后脱敏日志，并执行完整门禁。

## PC-41 总分本地加权与每次一张

**状态：已完成**

- 问题：同一张照片多次评分得到不同总分。两个来源：模型在五个维度之外还要独立采样一个综合分；
  同一请求里的多张照片共享上下文，候选池一变，邻居就变，分数跟着变。
- 契约：升级到 `v4`，`AestheticReviewEntry` 去掉 `score`；四个客户端的结构化输出 schema 同步去掉。
  模型即使自行返回 `score` 也会被完全丢弃。
- 总分：由 `AestheticScoreTotal` 按用户设定的五维权重在本地加权算出。全程整数运算，
  `(2 × 加权和 + 权重和) / (2 × 权重和)`，不经过浮点，跨机器可复现；权重全为 0 时退回等权。
- 权重：范围 0–5，默认等权，存 `UserDefaults`。控件放在侧栏 AI评分区块，评分前后都可调整——
  维度分已经付过费，重新拖动只重算总分与排序，不发请求、不产生费用。
  权重变化不修改任何已保存的维度分，也不回溯改变已作出的保留/淘汰决定。
- 传输窗口：`maximumPhotosPerReview` 从 5 改为 1，每张照片单独成为一次请求。
- 连带修复：`windowCapacity == 1` 时"避免落单尾部"会算出 `windowSize = 0`，游标不前进，
  规划死循环；该规则现在只在容量 ≥ 2 时生效。
- 连带修复：候选池规模曾复用 `maximumPhotosPerReview`，两者语义无关。拆出
  `candidatePoolMultiplier = 5`，否则窗口改小会让候选池塌缩到与保留目标同大，AI 失去挑选空间。
- 代价：48 张候选的请求数从 10 升到 48。图片 token 总量不变，提示词不再摊薄，输入约 +55%；
  4 秒基线间隔按 5 张大请求定的，单图请求下已明显偏保守，是下一步可收的部分。
- 已验收：183 项测试零失败；隐私、演示、PC-19 至 PC-39 与 PC-41 门禁、Xcode Debug 构建全部通过。
